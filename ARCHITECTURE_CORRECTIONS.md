# Architecture Corrections — read this before an interview

The phase1–4 `.md` docs in this repo were generated by a coding agent and contained
claims that didn't match the actual code. This file records exactly what was wrong,
what's true now, and what changed — so you can speak to the *real* system instead
of the documented one.

## 1. Model provider: Groq, not Claude

**Docs claimed:** Claude Haiku (router) + Claude Sonnet (reasoning), via the Anthropic API.

**Actually true (unchanged by this fix):** Everything runs on **Groq**.
```python
# app/config.py
ROUTER_MODEL    = "llama-3.1-8b-instant"     # triage / routing
REASONING_MODEL = "llama-3.3-70b-versatile"  # reasoning + tool calling
```
There is no Anthropic API call anywhere in this codebase. The Anthropic API in artifacts is unrelated — this project's LLM calls all go through `groq.Groq()`.

**What to say in an interview:** "I used Groq's Llama 3.1-8b as a cheap/fast triage
router and Llama 3.3-70b for reasoning — a two-tier model strategy to keep routing
cheap and only pay for a strong model on turns that actually need reasoning." That's
a completely legitimate, defensible design. Just don't say "Claude."

## 2. Tool execution: was two implementations, now genuinely one

**Docs claimed:** text (`router.py`) and voice (`gemini_client.py`) both call the
same `execute_tool()` entrypoint in `tool_executor.py`.

**Was actually true before this fix:** only the **voice** path called `execute_tool()`.
The **text** path (`workflow.py` → `agent_node()`) had its own separate, synchronous,
one-tool-at-a-time loop that called functions directly from a hardcoded
`AVAILABLE_TOOLS` dict — it never touched `tool_executor.py`.

**Now true, after this fix:**
- `workflow.py` builds its Groq tool schema from `tool_registry.schemas` (the same
  registry the voice path uses), converting the registry's Gemini-style types to
  Groq's JSON Schema format via `_to_groq_json_schema()`.
- `agent_node()` is now `async` and dispatches every tool call through the shared
  `execute_tool()`, executing multiple calls in one turn concurrently via
  `asyncio.gather` — matching what the voice path already did.
- `retrieve_rag_context` is deliberately excluded from the text path's tool list,
  because text still uses deterministic pre-fetch (`rag_node`, driven by the
  router's `needs_rag` decision) rather than letting the model decide whether to
  retrieve. **This is an intentional asymmetry, not an oversight** — see the note
  in `workflow.py` above `_TEXT_TOOL_NAMES`. Be ready to explain *why*: text has
  room for a synchronous pre-processing step before the reasoning call; voice's
  real-time audio stream doesn't, so voice leaves retrieval to the model's judgment
  via a tool call instead.

**What to say in an interview:** "Text and voice share one tool registry and one
execution core (`execute_tool`); each interface just translates that into its own
provider's function-calling schema. RAG is the one deliberate exception — text
pre-fetches context deterministically before the model runs, voice fetches it via
a tool call, because voice's real-time constraint doesn't allow a synchronous
pre-processing step."

## 3. Calendar storage: was JSON, now SQLite

**Was:** a flat `./data/calendar_events.json` file, rewritten in full on every write.
**Now:** `./data/calendar.db`, a real SQLite table with an autoincrement id and
`created_at` timestamp. Existing data was migrated (see git history / the `.migrated_bak`
file). This removes an easy "why not just use a database" question with no real
tradeoff lost — SQLite needs zero extra infrastructure.

## 4. RAG retrieval: no relevance floor → now has one

**Was:** `retrieve()` always returned the top-k nearest chunks, even when the best
match had near-zero actual relevance to the query (Chroma always returns *something*
close in vector space, whether or not it's actually related).
**Now:** results below `MIN_RELEVANCE_SCORE = 0.30` similarity are filtered out before
they ever reach the prompt. Verified with a unit test: a query with one strong match
and two noise chunks now correctly returns only the strong match.

**What to say in an interview:** "I added a relevance floor because vector search
always returns *a* nearest neighbor — without a threshold, an irrelevant chunk gets
injected into the prompt with the same confidence as a real match. 0.30 is a starting
point; the honest next step is tuning it against the eval set's retrieval precision
numbers rather than picking it by feel."

## 5. Memory writes: had a race condition → now locked + atomic

**Was:** `save_semantic_memory()` / `save_episodic_memory()` did a plain
`open(...).write()` with no locking. Two sessions consolidating near-simultaneously
(realistic once both a text and a voice session exist) could interleave writes and
corrupt the JSON file.
**Now:** a process-wide `threading.Lock` held across the full load → merge → save
span (not just the final write, which would still leave a read-modify-write race),
plus atomic writes via temp-file + `os.replace()` so a crash mid-write can't leave
a half-written file. Verified with a 30-thread concurrent-write stress test — no
corruption, valid JSON every time.

**Known limitation, stated honestly:** this is a **single-process** safeguard
(`threading.Lock`), not a multi-process one. It's correct for how this app actually
runs (one Python process). At real scale, this data belongs in SQLite/Postgres with
row-level writes, not flat JSON files with an in-process lock — say this proactively
if asked about scaling, don't wait to be caught on it.

## What did NOT need fixing

- The voice path's tool integration (`gemini_client.py` → `execute_tool`, with real
  `asyncio.gather`) was accurately described. It was already correct.
- The eval harness (`run_evals.py`, `eval_report.json`) is real and produces
  believable, imperfect numbers (74% intent accuracy, 26% retrieval precision pre-fix).
  Re-run it after these changes — precision should improve now that irrelevant
  chunks are filtered before scoring, but say the actual number you get, not this one.
